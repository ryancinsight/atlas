## Context

Atlas intentionally gives members one shared Cargo target directory. Cargo's fingerprint and dep-info records do not identify the source checkout that produced a proc-macro or other package artifact. Two exports with identical relative dependency names can therefore reuse an artifact compiled from different source bytes. Apollo's retained release-macro incident recorded a scratch-checkout path and an obsolete parser diagnostic while the canonical source accepted the new syntax.

A Git revision alone is insufficient for a dirty checkout, a branch name is not an identity, and a Cargo fingerprint is an implementation detail rather than a stable contract. A second source tree must not silently overwrite the first tree's record or artifact.

## Decision

### Stable scope and record

`scripts/atlas_build_records.py` owns one record for each build scope (`scripts/atlas_build_inputs.py` computes its dimensions and dependency data, and `scripts/atlas_build_identity.py` runs the lease protocol that reads and writes it): shared target directory, package, profile, target triple, feature set, toolchain identity, build-affecting environment digest, effective Cargo configuration digest, dependency-closure digest, the caller's stable command key, and the selection: every package the command builds. Cargo unifies features across one invocation's packages, so a shared dependency's variant, and the file a record names for it, depends on the whole selection; a record and a sibling record stand in only for a run of the same selection. The environment digest covers `CARGO_PROFILE_*`, `CARGO_BUILD_*`, `CARGO_TARGET_*`, `CARGO_UNSTABLE_*`, `CARGO_HOST_*`, and `CARGO_ALIAS_*` (an `[alias]` table entry set as env, which can itself carry compile-affecting flags, e.g. `CARGO_ALIAS_CLIPPY="check --config build.rustflags=[...]"`) (excluding `CARGO_TARGET_DIR`, already the record's own canonicalized `target_dir`), and a fixed set (`CARGO`, `CARGO_ENCODED_RUSTFLAGS`, `CARGO_INCREMENTAL`, `RUSTC`, `RUSTC_BOOTSTRAP`, `RUSTC_WORKSPACE_WRAPPER`, `RUSTC_WRAPPER`, `RUSTFLAGS`); a leading `env NAME=VALUE ...` prefix on the build command is parsed and overlaid on the ambient environment first, so a variable it sets is covered exactly as if it were exported. Rustdoc-only inputs -- `RUSTDOCFLAGS`, `CARGO_ENCODED_RUSTDOCFLAGS`, `RUSTDOC`, and their `CARGO_BUILD_*`-prefixed spellings (`CARGO_BUILD_RUSTDOCFLAGS`, `CARGO_BUILD_RUSTDOC`) -- are deliberately excluded, even though the record does name doc-unit fingerprint files (`discover_artifacts` walks a package's whole `.fingerprint/<pkg>-<hash>/` directory, which holds `doc-lib-*`/`output-doc-lib-*` beside the compile-unit files). Exclusion is sound because Cargo's own fingerprint scheme makes the omission moot, not because a later mismatch here would catch a stale one: Cargo's per-unit fingerprint for a `doc` unit already incorporates that unit's effective rustdoc flags, so `cargo doc` unconditionally re-invokes rustdoc -- rewriting `doc-lib-*`/`output-doc-lib-*` -- whenever those flags differ from the last run, before this scheme ever reads the resulting bytes. There is consequently no stale-doc case to guard against: whatever a given `cargo doc` run writes already reflects that run's own flags, so `run_build`'s matched branch simply adopts those bytes into the record, unconditionally once settled, rather than comparing them against a prior expectation -- adoption, not mismatch detection, because Cargo already enforced freshness before this module looked. The actual reason for exclusion: the pre-push gate runs clippy, nextest, and `env RUSTDOCFLAGS=... cargo doc` under one shared command key for one package specifically so they read one record when their selections match; including a rustdoc-only input would give the doc step's `env`-prefixed invocation a different digest from the clippy and test steps' plain ones, splitting that one record into two mutually-stale halves and cleaning the whole dependency closure on every push instead of once. The configuration digest covers, for every directory between the execution root and the filesystem root, both `.cargo/config.toml` and the legacy `.cargo/config` when both are present (Cargo itself prefers the extensionless file when both exist at one level; this digest hashes both rather than picking one, so either changing is visible), `$CARGO_HOME/config.toml` and `$CARGO_HOME/config` the same way (with `$CARGO_HOME` itself resolved from the same `env`-prefix-overlaid environment as the environment digest, never `os.environ` alone, so an `env CARGO_HOME=<h> cargo ...` command prefix is not invisible to it), and any `--config` command-line argument -- a file path (hashed by content, resolved against the execution root exactly as Cargo resolves it -- never this process's own working directory -- when relative) or inline TOML text (parsed the same as a file's content). Every config source's own `include` value (stable since Cargo 1.97) is followed recursively and cycle-guarded, so an edit confined to an included file is not invisible; Cargo accepts `include` only as a list of strings (`["a.toml"]`) or a list of tables (`[{ path = "a.toml", optional = true }]`, `optional` skipping a missing path exactly as `is_file()` already does here) -- never a bare string, which Cargo itself rejects, so this digest does not treat one as a one-element list either. Each config's text is parsed by this checker's own `tomllib` (strict TOML 1.0), one grammar step stricter than Cargo's own parser, which additionally accepts a trailing comma after an inline table's last element, an inline table split across lines, and the TOML 1.1 string escapes `\e`/`\xHH`; a leading UTF-8 BOM is stripped before parsing (Cargo accepts one), and any other parse failure fails closed by raising rather than silently treating the config as `include`-free, naming the offending file. That raised error is surfaced through the pre-push gate's identity-branch classification (`classify_gate_step`'s `atlas-build-identity:`-prefixed match, reported as "source identity blocked ... no artifact was accepted"), never its environment-failure branch (reserved for a lockfile collision or a `--locked cargo metadata` failure) -- the two are distinct verdicts and a config parse failure is the former. A directory config is framed by its depth from the execution root and its filename, never its absolute path, so a config file committed inside the repository itself does not look new merely because the pre-push gate exports each push to a fresh temporary directory; such an in-tree `.cargo/config.toml` is itself one of the sources this digest covers, at depth 0, alongside the stack-mirrored config that sits outside the diffed repository -- one case does not make the other irrelevant. The command key names the build-entry-point dimensions without treating `clippy`, tests, and documentation as different source identities -- true because every dimension besides the command key, including the environment and configuration digests, is identical across those three steps for one package when they build the same selection; a step whose selection differs keeps a record of its own. The record is stored atomically under `target/.atlas/source-identity/`, inside the existing cache root. It contains the canonical source root, full Git revision, clean/dirty state, source-tree digest, resolved dependency closure, build dimensions, and hashes of the discovered or explicitly supplied package artifacts. Record version is 6; versions 1 through 5 are stale (version 5 has no package selection; version 4 names Git packages' files, which version 5 no longer records; version 3 predates the configuration digest and every field it added, so it is treated as stale rather than failing the current version's field-presence check). Malformed or unsupported current-version records fail closed.

Staleness compares content only: the revision, clean/dirty state and tree digest, the build dimensions, the dependency closure, and the artifacts. The source root is recorded for diagnostics and lease ownership but never compared, and path packages inside the workspace are named by their workspace-relative directory, because cargo spells a path package's ID with its absolute directory and the pre-push gate builds each push in a new temporary export. Every source tree is diffed against `HEAD`; the gate export's index carries stat data, so that diff compares stats rather than re-hashing the tree.

The record path excludes the source revision deliberately. A source transition must contend with the existing owner of the same build scope; otherwise a second source tree could acquire a different lock and overwrite the first record.

### Mismatch and ownership

A missing, malformed, or mismatched record is stale. The gate resolves the package's reachable path and Git dependency closure, acquires the scope lease, cleans the packages whose source content may differ from what built their artifacts (below), then runs the requested build command and writes the record only after success. Ordinary matching builds reuse the existing artifacts without cleaning. Registry and Git packages also carry a digest of their unpacked source content, since Cargo does not fingerprint edits there. That digest is memoized under `.atlas/source-identity/package-source/` against a stat fingerprint of the same file set (each path, size, and modification time, and each symlink's target), and a stored entry is written only when the fingerprint after the read equals the one before it; a content edit that preserves both size and modification time is not detected, the bound Cargo's own fingerprint places on path packages. Re-reading every file instead was rejected: a run takes the snapshot up to four times, the last under its closure's exclusive leases, and one kwavers pass read 587 MB across 437 registry packages in 71 s, and a kwavers push was still in its post-build snapshot, holding about 110 exclusive leases, 25 minutes after it started while every push sharing a dependency waited.

The lease stores owner root, revision, package, target directory, token, and expiry. The OS file lock is authoritative while a process is alive; the expiry is diagnostic only, since a crashed owner releases its lock and that alone makes the lease reclaimable. The lock covers byte 0 only and the owner record starts at byte 1, because a Windows byte-range lock refuses reads of the locked range from every other handle; keeping the lock on byte 0 keeps exclusion with holders that predate the offset. A lease is held shared or exclusive. A held lease file is never empty: an earlier checker that finds it empty writes byte 0 and crashes on the lock, so an opener writes a placeholder byte before it locks, and a write refused because a holder locked the byte meanwhile is left to that holder's byte. Only an exclusive holder writes the record, which it overwrites and then cuts to length rather than truncating first. Windows takes the byte-0 lock with `LockFileEx`, whose shared mode conflicts with the `msvcrt.locking` exclusive lock of earlier holders, and treats only `ERROR_LOCK_VIOLATION` as contention. POSIX takes it with `flock`, the call earlier holders used; `fcntl` record locks would not see theirs. A check only reads artifacts, so it probes shared.

Requests are served in arrival order. Each request creates a ticket file in the lease's queue directory, named by the system-wide monotonic clock at arrival, the mode, and a run identifier shared by every ticket of the run, and holds an exclusive lock on it until it releases the lease. A ticket's place is `(arrival, run)`: a strict total order, the same at every lease, because two runs never share a run identifier and the mode, which differs from lease to lease for one run, is no part of it. An earlier version compared whole ticket names, where the mode letter decided a tie, and two runs with one arrival and crossed modes (one exclusive at `a` and shared at `b`, the other the reverse) each queued behind the other until the deadline; a ticket of a checker that predates run identifiers uses its pid and uuid as its run, so it ties with nothing. An exclusive request waits for every earlier live ticket; a shared request waits only for earlier exclusive tickets. Readers that arrive together therefore share, and a waiting writer holds back every later reader, so a stream of readers cannot starve it. A holder that releases and asks again as a new run gets a new ticket behind the requests already waiting, so a repeating holder cannot starve them either. A waiter keeps its ticket for its whole wait, at every lease its claim needs (below). Writer preference alone was rejected: it still lets a repeating writer win every race against a polling waiter, which is the failure observed. Liveness is probed with a shared lock, so concurrent probes never make a dead ticket look held to one another. A requester that loses the race between creating its ticket and locking it retries under a new name with the same arrival; it closes the losing handle on every path. On POSIX a peer that saw a new ticket unlocked can still unlink it after its requester locked it; each attempt checks that the ticket's path still names the locked file and re-creates it with the same arrival if not, so the ticket is missing for at most one polling interval. Every request scans the whole queue and removes each dead ticket, whatever its mode or position. A dead ticket that cannot be removed because a probe has it open at that moment, the only Windows case, is removed by the next request, so dead tickets never outlive the next request. Holders whose checker predates the queue take no ticket and are ordered by the lock alone until they fetch the current checker. The test suite runs that pre-mode lease module itself, vendored byte for byte from atlas f96b218, to prove the two protocols exclude each other; the vendored copy and its interop tests are removed once every member's pinned atlas checker is at or past #320, when no hook runs the pre-mode protocol any more.

A live conflicting owner refuses the operation without cleaning, deleting, or overwriting artifacts; the command-line `run` entry point, which the pre-push gate invokes, first waits for that owner with backoff, bounded by `--lease-wait-seconds` across every lease and both acquisition phases below, and fails without the lease when the bound passes. The recorded expiry is reported but never ends the wait, and holders do not renew it: the lock already proves liveness, so renewal would only refresh a field nothing decides on. A run takes every lease of a phase together or none, and while it waits it holds no lock. At its first look it files a ticket at every lease it needs, under the run's arrival, and keeps all of them until the claim is taken or refused, whether the lease is free or not. A request is blocked by a conflicting ticket that arrived before it, whether that ticket holds the lease or waits for it, and by a conflicting ticket that arrived after it only while that ticket's holder holds the lock (probed by a transient take); a later request that is itself waiting does not block an earlier one. Once nothing blocks it at any lease, the run takes all its locks in one pass; a peer that took one between the look and the take makes the run give the locks back, keeping its tickets, and look again. Every phase of one run (the shared claim, then the exclusive one after a mismatch) carries the run's arrival and run identifier, so the second phase goes before the requests that are waiting when it asks. Deadlock freedom: a run waits holding no lock and takes locks only in one pass after every one of its leases is clear, so no run waits for another while holding what the other needs. There is no hold-and-wait, and so no cycle of waits. Progress: order the runs by place, `(arrival, run)`. A later request is not granted while an earlier conflicting ticket stands at one of its leases, and a run's tickets stand at every lease of its claim for its whole wait, so no later arrival overtakes it at any lease (a writer that needs `a` and `b` is not passed by readers alternating between them). The earliest waiting run therefore has only holders in its way. Holders never wait, so each releases within its step, and the run is granted. Every run waits for the holders ahead of it and the earlier runs that conflict with it, each in turn: a finite set, since later arrivals queue behind it. The price is an idle convoy: a later request that conflicts at a lease where the waiting run is not itself blocked still waits behind it, bounded by the earlier runs' holds. The one bound `--lease-wait-seconds` covers the whole run, and the refusal names the lease and the holder it was blocked at. A run that waits behind a single peer step therefore waits about that step. A chain of conflicting runs waits for each in turn, and a step that holds for its full length (about 12 minutes for a 12-package metis step on 2026-10-02) leaves one run's worth of the 900 s bound. The argument covers runs of one checker. A gate keeps the checker copy it fetched for its whole run, so while checkers of both protocols are in use an old run, which takes its leases one at a time in name order and holds the earlier ones while it waits for a later one, can hold a lease a new run needs while it waits at one the new run's earlier ticket guards; the new run then waits for it, and the old run for the new run, until the new run's `--lease-wait-seconds` ends. Reproduced with the module of main `f5d4781` and this one in one target: the new run was refused after its full 4 s wait and the old run took its lease at 4.07 s. The new protocol sees an old run as an ordinary holder and cannot back off from it, so the mix is bounded by the deadline and lasts until each in-flight gate ends, longer for a clone whose stack origin is stale. Rollout condition: this interval is accepted; a gate it refuses names its blocker and is pushed again once the older gates end. Closing a claim appends one line to `claims.jsonl` in the lease directory: the run and its place, the leases and which were exclusive when the claim was taken (the run downgrades most of them before its command), `wait_s` from the request to the take, `hold_s` from the take to the release, who blocked it, and `phase`, the claim's number within the run (1 for its first, 2 for the exclusive claim after a mismatch, more when a clean widens). The wait bound is read against these records: a run's wait is at most the holds of the claims it waited for. The log rotates at 1 MiB, keeping one earlier file; closers rotate under a lock and re-check the size under it, so one rotation happens however many closers see the log over its bound, and a rotation that fails (Windows refuses to replace a log a peer has open) never costs the record. An unlocked lease is reclaimed whatever its content: no live process can hold it, and a writer killed mid-record leaves a partial one. A malformed record fails closed.

A run takes the lease of the package its command builds exclusive and the leases of its clean-closure dependencies shared, then reads its record. Only when the record matches exactly (source, build dimensions, dependency closure, and every artifact file it names) does the run keep that shape. Otherwise it releases every lease, takes them all exclusive, and reads the record again, because a holder may have rebuilt the scope in between. It cleans only if the record still does not match. Releasing before asking again, rather than upgrading in place, keeps two upgraders from each holding the shared lease the other waits for. A missing record whose build and source a sibling command key's record already names does not clean; it is retaken exclusive like any mismatch. Before its command, a run with a record (its own exact match, a sibling's, or the one a partial clean compared), every file of which was read under the run's leases, downgrades every lease it did not just clean, other than its own package, to shared: those scopes are then only read, exactly as on a matched run. A run with no such record (a full clean, or a custom clean command whose effect is unknown) keeps every scope exclusive, because it can find those packages' artifacts only by discovery; so does a run of declared artifact paths, whose record names none of the closure's files. A closure package the record names no file of is held shared and left unrecorded, as on a matched run. On Windows the downgrade never releases the lease: a shared `LockFileEx` lock over the held exclusive byte, then one unlock (the first unlock of an exclusive-plus-shared range releases the exclusive lock, per the `LockFileEx` remarks); on POSIX a `flock` conversion, which unlocks before it relocks, guarded by the request's exclusive queue ticket, re-created first if a peer's collection removed it, so a racer that queued backs off; the ticket is re-filed as shared under its original arrival after the conversion, so a writer queued meanwhile still waits. Any other request can still land in a non-atomic `flock` conversion (a holder from before lease modes takes no ticket, and a queued request takes the lock before it backs off for an earlier ticket); the one conversion attempt then fails and the run is refused holding nothing, never retried, because a later retry could not tell whether the taker cleaned the scope meanwhile. Releasing and asking again was rejected: a writer queued behind the lease would enter between the clean and the command, clean again, and hold the closure through its own command.

Under a shared lease, Cargo can still write into a dependency's `deps/` and `.fingerprint`. It writes new metadata-hash variants for another profile, feature set, or check mode. It also rewrites the files a record names in place, under the same name, whenever it rebuilds that unit, and a changed modification time alone makes it rebuild; the rewritten file can be byte-identical. While rustc rewrites a file, a concurrent read of it on Windows fails with a permission error. The run therefore hashes only the dependency files its record names, found by name and never by discovery; variants beside them are outside every comparison. A named file that cannot be read, or whose content changed, is a mismatch and sends the run through the exclusive path: a conservative rebuild, never an accepted artifact. After the command, the run hashes every dependency file its record names again, because its own command may have rebuilt them in place: an export's fresh modification times make Cargo rebuild path dependencies, and rustc embeds the build's path in the bytes it writes. A file counts as read when two consecutive reads give one digest with its size and modification time unchanged across both. Each file gets up to one second, never past the run's wait deadline. A file whose reads succeed but never agree, because another reader's Cargo keeps rewriting it, is recorded unverified; the next run sees a byte mismatch there and cleans that file's package. Only a file that cannot be read at all in that time keeps the digest verified before the command. Only the packages the run holds exclusive are discovered afresh, and names its record lists for them are dropped, so a name their rebuild retired is not kept; every package held shared is hashed by the names its record, or the sibling record it downgraded on, lists. Carrying the pre-command digests instead was rejected: they describe the files before the command rebuilt them, so they are stale by construction. With real Cargo 1.97, pushing one commit repeatedly from fresh exports cleaned, per push: carried digests at a new path each push `[d,p], [], [d,p], []`; carried digests with a partial clean `[d,p], [], [d], [], [d], []`; re-hashing at a new path each push `[d,p], [], [], []`; carried digests at one fixed path `[d,p], [], [], [], [], []`. Re-hashing avoids those cleans whether or not a member's hook reuses one export path. Which packages a mismatch cleans follows from what Cargo itself re-checks. A unit whose features, profile, dependencies, edition or toolchain change gets a new metadata hash or a rebuild in place, so none of those can leave a stale artifact; source content can, in two ways only. Cargo trusts a path package's artifact while its sources are older than it, so another tree's build of the same workspace-relative package can stand in for this one, and it never re-reads a Git or registry checkout. The record must also keep naming the variant the build uses: a unit's metadata hash folds in its features, its profile and its dependencies' hashes, so a renamed unit left in the record keeps naming a file the build no longer uses, which another tree could then overwrite unseen. Source content renames nothing; a variant is renamed only by the build dimensions or by the snapshot's shape. The shape is the snapshot without its content fields (a path record's repository identity, a Git or registry checkout's digest): every record's name, version, features, source and resolved manifest, the edges, and the workspace manifest. The resolved manifest is the package's `cargo metadata` entry after workspace inheritance, its absolute paths dropped: dependency tables with their features, `cfg` targets and kinds, the feature table, the edition and the targets. It is needed because `cargo metadata` unifies features across `cfg` tables and dependency kinds: a judge moved a feature of a path dependency from a never-true `cfg` table to the plain one, which renamed that dependency's variant with its own record unchanged. Git and registry records carry it too: another judge edited a Git checkout's manifest the same way, renaming the Git package and through it a path dependent, while every record but that package's content stayed equal. The workspace manifest's bytes are needed because its `[profile]` tables enter every unit's hash and no package entry. The lockfile is not hashed: the overlay rewrites the working lock on every build, and every revision and version it pins is already in a record. Which variants a shape change renamed cannot be read from the snapshot, so a shape or dimension change cleans every path package, as does a missing record. Otherwise only content moved, and a mismatched run cleans each path package whose source identity moved, its own package when its source moved, and the path packages owning a changed recorded file, or every path package when a changed file cannot be attributed to exactly one. In every case it cleans each Git package whose build stamp names other content than its checkout holds. The build stamp lives in the target, at `.atlas/source-identity/git-build/<sha256(name, source, profile, target)>`, one per build directory, because a record describes only its own runs' builds: a judge reproduced two roots sharing one checkout, where the second root built an edit and the first, its record matching once the first edit's bytes were written back, reused the second's artifact; and a run whose sibling command key's record stood in for its own reused an artifact another key had built from an edit since restored. For each Git package it cleans or finds unstamped, a run writes a building sentinel, which equals no content digest, before its clean and its command, and the content digest only after its command and its final snapshot, the content unchanged across both; a run that fails or is killed in between leaves the sentinel, so the next run cleans the package rather than trusting what the target may already hold from the interrupted build. A package whose stamp already matched gets no sentinel: an edit written to its checkout after the snapshot, built from, and reverted before the next run is not seen (ATLAS-IDENTITY-MIDRUN-GIT-EDIT). A stale stamp also makes a matched or sibling run clean that package, and a custom clean command, whose effect is opaque, is followed by a Cargo clean of the stale Git packages. The stamp names one build directory, and the clean that invalidates it carries that directory's `--profile` (`dev` for `debug/`) and `--target`, so each stamp vouches only for artifacts a clean could reach; a judge reproduced a stamp spanning the target, where a debug run cleaned `debug/`, stamped the edit, and a release run then reused `release/`'s artifact of the original. A package with no stamp in a build directory was never built there by a run of this checker since stamps began, and its artifacts there are trusted, the bound accepted below for builds outside this checker; cleaning it instead would have run `cargo clean -p`, which deletes every variant of that crate name, at each first-party revision bump. Without a readable record, every path package and every Git package with a stale stamp is cleaned. A changed file the run cannot attribute to exactly one path package cleans every path package. Registry packages are never cleaned. Records name only path packages' files: a Git package's artifacts are tied to its checkout content by the build stamp instead, and hashing every variant of every Git package in the shared target cost each run minutes. Comparing the whole snapshot and cleaning the non-registry closure on any difference was rejected: a ritk-codecs push adding two dependencies cleaned 35 packages and held them exclusive through its command, 34 of them unedited Git checkouts, while metis and athena pushes failed after the 900 s wait. Cleaning every path package whenever the root's source or any path record moved was rejected: under the development overlay every stack member is a separate-repository path package, so each push of a consumer cleaned and held them all exclusive, the serialization this rule removes. Narrowing that snapshot comparison per record (ryancinsight/atlas#418) was rejected too: a judge reproduced three real-Cargo cases (dev-dependency feature activation, a version bump, an edition change moving the implicit resolver) where its record named a variant the build no longer used. Under this rule each of them changes a path record, which is cleaned and rediscovered, or only a Git package's variant, which no record names. After a clean, a record entry for a file the clean deleted and did not rediscover under a new name is dropped, not carried forward at its pre-command digest: only a package the run held shared throughout may fall back to re-verifying its named file by settling, since only there could a transient read failure mean a live peer mid-rewrite rather than a file this run's own clean removed. The alternative, an exclusive lease for any window in which the command may write a dependency, was rejected: Cargo decides that only while it builds, so every command would hold every dependency exclusive, the starvation this design removes. The exclusive window is therefore one stale run, for the packages it cleaned. Their clean, the command rebuilding them, and the record written after it are a single step that cannot end earlier, and the hook's next step finds a matching record and reads shared. Concurrent readers still take turns at Cargo's own build-directory lock. A match guarantees that no run cleans a dependency underneath its readers. It does not guarantee that Cargo leaves the named files untouched, and nothing in the design relies on that.

The lease key is (package name, target directory), without the source revision or target triple. Two revisions of one source root produce the same artifact names, so a revision key would let them clean and overwrite each other; a cross-target build still compiles its proc-macro and build-script dependencies into the host directory, so a triple key would let two triples clean and rebuild one host artifact concurrently. The target resolver uses the Git common directory so a linked Atlas worktree still addresses the primary cache.

### Build entry points

The shared identity module is the single policy surface. The member pre-push gate builds an export of each pushed revision -- a checkout of it in a repository of its own, written by `read-tree -u --reset` run in the member so a partial clone fetches missing blobs, with `core.longpaths` set, at one short path per checkout that a run claims by lock and the next run updates in place, so links stay links, the index carries stat data, and unchanged files keep the times cargo fingerprinted -- in a temporary directory outside the stack's `[patch]` overlay, never the checkout, which a shared tree holds on a peer's branch or dirty. The export is a repository whose `HEAD` is the pushed commit and whose object store is the member's, so the module records the pushed revision as the source; the gate invokes the module with the export as `--root` once per step for every changed package before accepting clippy, tests, or documentation, all under `--locked` against the committed lock. One stable command key lets those steps share each package's record when they build the same selection. The integration composes with the existing conformance push guard in PR #277; it must not duplicate that guard or hand-edit member hook copies. Other build entry points use the same module when they compile packages, rather than implementing a second provenance format.

The module records artifact hashes after the command. It does not treat Cargo fingerprint JSON as a public schema, and it does not claim that a missing `.fingerprint` directory proves source identity.

## Known limits

Bounded by a no-regression-vs-main acceptance: main today has none of this effective-Cargo-configuration identity dimension, so each of these is a subset of what main already misses, not a new gap this ADR introduces.

- An alias (a config `[alias]` table entry, or a `CARGO_ALIAS_*` environment variable) that itself expands to a `--config <file>` argument is not followed to that file: this scheme parses the literal command line and the literal `env`-prefix environment, not what Cargo's own alias expansion would produce. A config-file alias reached this way is still covered indirectly whenever that file is also reachable through the ordinary directory walk, `$CARGO_HOME`, or an explicit `--config` argument already on the command line; only an alias-*only* path to a config file escapes it.
- A config using TOML 1.1-only syntax beyond the three cases this checker explicitly recognizes (trailing comma after an inline table's last element, an inline table split across lines, and the `\e`/`\xHH` string escapes) fails closed the same way: raised, not silently skipped, but not parsed either. Cargo's own TOML grammar is not formally specified as a grammar this checker's `tomllib` can be told to accept; each divergence found is added to the recognized set rather than assumed complete.
- A Git package's artifact built by a build outside this checker, from content other than its checkout holds when the next identity run stamps it, is reused; the stamp covers the package directory's content digest, so an edit outside that directory within the same checkout is not seen; and registry packages are never cleaned. Both are the bound Cargo itself places on those sources, which it never re-reads.
- Environment set by any mechanism other than a leading `env NAME=VALUE ...` command prefix or the ambient `os.environ` -- a `.cargo/config.toml` `[env]` table, a build script's `cargo:rustc-env=`, or a wrapper script that exports variables before invoking Cargo -- is invisible to `environment_digest`. The `[env]` table case is partially covered indirectly: a `.cargo/config.toml` edit changes `cargo_config_digest`, but the variable value it sets is not decomposed into the environment digest's own key/value view.

## Failure modes

- A dirty tree is identified by a digest of its Git diff and untracked or ignored source files; generated files under the resolved target directory are excluded; a matching revision with different content is stale.
- A source path or artifact outside the shared target is rejected before any clean.
- A full Cargo metadata graph is required when artifacts are discovered implicitly; an unresolved or name-ambiguous dependency closure fails closed. A discovered artifact belongs to the package with a target of exactly its name (the file name before cargo's metadata hash), never to one whose target name is a prefix of it.
- A build-affecting environment change produces a different record scope.
- A lockfile rewrite caused by the development overlay is excluded from the source digest only after the pushed lock has been checked and the working copy is restored.
- A live owner conflict returns a diagnostic naming the owner and revision and performs no destructive action.
- A failed build leaves the previous record unchanged and releases the lease.
- A missing or malformed record fails closed rather than accepting an unknown artifact.

## Consequences

- Shared-cache reuse remains ordinary and fast when source and build dimensions match.
- A source transition rebuilds the selected package, every path package when the snapshot's shape moved (otherwise those whose source moved or that own a changed recorded file), and the Git packages whose build stamp names other content or an unfinished build, without creating a second target tree; other Git and registry dependencies keep their artifacts and are held shared.
- Concurrent source trees cannot silently clean or overwrite each other's artifacts.
- The provenance record is derived cache state; removing it causes a conservative rebuild, not a false pass.
- The gate adds one deterministic identity check before compilation and retains the existing shared target root.

## Alternatives rejected

- A per-source target directory prevents reuse but forks the cache and violates the one-target budget.
- Manual `cargo clean -p` repairs one incident but does not protect a concurrent owner or record identity.
- Cargo fingerprint JSON as a public contract couples Atlas to an unstable internal schema.
- Cleaning the entire target on every source transition destroys unaffected artifacts and violates the rebuild-scope requirement.
- A repository-name filter on the clean set: 17 of 210 gated-package leases were last held exclusive by a member that does not gate that package (`cargo clean -p` of a Git package, which removes every variant of that name), but a filter would skip verifying the dependency artifacts the shared lease protects.
- Giving a blocked run's place up at the leases that are free, so that it keeps a ticket only where it is blocked (the first version of the claim): a writer that needs two packages is overtaken at the free one by readers alternating between them, and waits to the refusal (a judge's probe: 20 of 20 rounds). Keeping the place at every lease of the claim costs the idle convoy described above, accepted because the wait it adds is bounded by the earlier runs' holds. Strict global conflict-first-in-first-out across leases gives the same guarantee with no further benefit.
- Raising `--lease-wait-seconds`: it moves the refusal and keeps the starvation.
