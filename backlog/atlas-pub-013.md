## ATLAS-PUB-013 — A patch release that raises a dependency floor breaks already-published crates [patch] — todo
- outcome: no published version of a first-party crate becomes unbuildable because a later release of another first-party crate changed what its caret requirement resolves to. Five published versions are unbuildable today and cannot be repaired in place, because crates.io never overwrites a version: `leto` 0.41.0, 0.42.0, 0.43.0 and 0.43.1, and `hephaestus-core` 0.19.0.
- basis 2026-10-05 (crates.io sparse index, `static.crates.io` `.crate` contents, member workflow runs): all five declare `aequitas ^0.2.0` and `eunomia ^0.8.0`, none is yanked, and no `leto 0.42.x` or `0.43.x` successor exists. `aequitas 0.2.1` (2026-10-03; `e433dbd` "Require the eunomia that compiles" and `bfc9b78` "Require eunomia 0.9", following `bf16408` "Follow eunomia's unit-scalar rename") raised its `eunomia` floor from 0.8 to 0.9, and `eunomia 0.9.0` published the same day. `^0.2.0` admits `0.2.1`, so a fresh resolve of any of the five now selects `aequitas 0.2.1` alongside their own `eunomia 0.8.x`. `aequitas 0.2.1` carries the `T: UnitScalar` bound on the impl block of `Quantity` (`src/quantity/construction.rs:7-10`, importing `UnitScalar` from `eunomia` at `:1`), while `leto 0.42.0` bounds the same `T` with `eunomia 0.8`'s trait (`src/application/stencil.rs:4` and `:100`). The two are different traits, so `in_unit` is unsatisfiable. `leto 0.45.0` is coherent (`aequitas ^0.2.1`, `eunomia ^0.9.0`), so the 0.45 line is unaffected.
- observed: apollo `Crates.io Release` run 37275972653 (schedule) failed 2026-10-05T07:07 in `Publish pending versions / Plan version-change publish` with `error[E0599]` at `leto-0.42.0/src/application/stencil.rs:121:23` and `:122:23`, unsatisfied `T: eunomia::traits::unit::UnitScalar`. The same workflow is green since (run 37324518559, push, 14:25) because the tree moved to `leto = "0.45.0"` (`repos/apollo/Cargo.toml:96`); gaia (run 37332869262) and hephaestus (run 37323425761) are green for the same reason. The tree is past the break; the registry is not, so a consumer resolving `leto = "0.42"` or `"0.43"` still fails.
- guard: the push-mode publish plan resolves the pending set against the registry, which is why the break surfaced there, but nothing resolves the *already-published* dependents. Add a published-consumer check: for each crate about to publish at version V, enumerate from the index the published versions whose requirement admits V and build them, failing with the consumer's name and version. Until it lands, the policy form is to refuse a patch release that moves a dependency's requirement to a different minor.
- priority: correctness; needs: a decision on the five unbuildable versions first. A `leto 0.42.1` and `0.43.2` plus `hephaestus-core 0.19.1`, cut from 0.45-compatible sources, is the only forward repair; yanking `aequitas 0.2.1` is not, because it would break the consumers already on `^0.2.1`. That repair must land before the guard, since the guard turns these five into a red gate.
- acceptance: the scan that produced the basis, re-run, reports zero trapped versions; the guard fails on a fixture that raises a dependency floor in a patch release.
