outcome: every gate that reports against a checkout states that checkout's distance from its upstream, or refuses to report — so a stale local checkout can never masquerade as current-default evidence.
background: four false findings this session traced to gates reading whichever revision was checked out (a `main` 58 commits behind, an ADR-index drift that was really the checkout, not the source). Fixed in `7481561` for the ADR gate; the fallback-to-`origin/main` case is the one that matters, since a detached HEAD (no `@{upstream}`) is exactly the stale case.
open: `atlas-conformance.py --worktree` has the same exposure — it bypasses `check_clean_revision`'s clean-tree/gitlink-match guard, and is what runs while peers hold dirty trees (every conformance number this session came from it).
evidence (2026-09-23): corrected the same day. An earlier note here claimed a pin advance was blocked because the member clones lacked their pinned objects — that was wrong, and the way it was wrong is worth keeping. `--pinned --verify-oracle` failed with `git ls-tree failed for member 'CFDrs' at 4dd89942… (exit 128): fatal: not a tree object` from an isolated worktree, which reads as a missing object. Every member's pinned object is in fact present locally (`git cat-file -t <pin>` succeeds for all 28). The cause was the worktree's own `repos/<member>` paths being empty directories: `git -C repos/CFDrs` resolved *upward* into the superproject and looked for the member's commit in the wrong object store. Junctioning each member into the worktree fixed the read, and the advance was re-run with the census regenerated (233 production / 137 test-bench, `--verify-oracle` exit 0); the PR that carried it (#261) was later closed unmerged over unrelated ratchet/pin-freshness gate failures, so the diagnosis stands but that pin set never landed. Lesson for any second worktree doing pinned reads: give it real member paths, or `git -C` silently answers from the superproject.
